
Overview

The Distributed Task Processing Platform stores information about users, jobs, job execution history, results, and notifications.

The database is responsible for:

- Persisting jobs
- Tracking job status
- Maintaining execution history
- Storing result references
- Managing user notifications

---

Entities

1. User

Represents a registered user who submits jobs to the platform.

Fields

user_id
email
password_hash
created_at
updated_at

Notes

- "user_id" is the primary key.
- Passwords are never stored directly.
- "password_hash" stores the encrypted password.

---

2. Job

Represents a unit of work submitted by a user.

Fields

job_id
user_id
job_type
status
payload
progress
retry_count
worker_id
version
failure_reason
created_at
updated_at

Notes

- "user_id" identifies the owner of the job.
- "job_type" identifies the task category.
- "status" can be:

PENDING
RUNNING
COMPLETED
FAILED
CANCELLED

- "payload" contains input data required for execution.
- "progress" stores execution percentage.
- "retry_count" tracks retry attempts.
- "worker_id" stores the currently assigned worker.
- "version" is used for optimistic locking and race-condition prevention.
- "failure_reason" stores error details when a job fails.

---

3. Result

Represents the output generated by a completed job.

Fields

result_id
job_id
result_type
size
result_url
created_at

Notes

- "job_id" links the result to a job.
- "result_type" can be:

PDF
IMAGE
VIDEO
ZIP
TEXT
JSON

- "result_url" points to external storage (e.g., S3).
- Large files should not be stored directly in PostgreSQL.

---

4. Job Event

Stores the complete execution history of a job.

Fields

event_id
job_id
event_type
worker_id
details
created_at

Notes

Example event types:

CREATED
ASSIGNED
STARTED
FAILED
RETRIED
COMPLETED

This table acts as an audit log and helps reconstruct the lifecycle of a job.

Example:

CREATED
ASSIGNED -> Worker 17
FAILED -> API Timeout
RETRIED
ASSIGNED -> Worker 42
COMPLETED

---

5. Notification

Stores notifications sent to users.

Fields

notification_id
user_id
type
message
metadata
created_at
read_at

Notes

Examples:

JOB_COMPLETED
JOB_FAILED
JOB_CANCELLED

- "read_at" is NULL until the user reads the notification.
- "metadata" stores additional notification data.

---

Entity Relationships

User → Job

One User → Many Jobs

A user can submit multiple jobs.

---

Job → Job Event

One Job → Many Job Events

A job can have multiple events throughout its lifecycle.

---

Job → Result

One Job → Zero or One Result

A result exists only after successful completion.

---

User → Notification

One User → Many Notifications

A user can receive multiple notifications.

Indexing Strategy

Jobs Table

Primary Key

job_id

Secondary Indexes

user_id
status
created_at

Composite Index

(status, created_at)

Used for scheduler queries such as:

SELECT *
FROM jobs
WHERE status='PENDING'
ORDER BY created_at;

---

Design Decisions

Why Separate Result Entity?

- Results can be very large.
- Jobs remain lightweight.
- Supports external storage systems.

---

Why Separate Job Event Entity?

- Preserves execution history.
- Enables debugging and auditing.
- Tracks worker reassignment and retries.

---

Why Not Store Workers in PostgreSQL?

Workers are runtime components.

They:

- Start and stop dynamically.
- Send heartbeats frequently.
- Are better tracked through Redis or in-memory registries.

Therefore workers are treated as infrastructure components rather than persistent entities.
